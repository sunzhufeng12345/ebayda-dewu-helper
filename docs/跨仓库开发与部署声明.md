# 跨仓库开发与部署声明

本项目由两个 Git 仓库组成：

- BPMS：API、网页、数据库迁移、任务队列和凭据服务。
- Windows 助手：深链、任务执行、得物浏览器自动化和安装包。

两个仓库不直接合并 Git 历史。跨仓库功能使用同名或带相同功能编号的两个分支，并在 PR 中写明依赖关系。

## 环境职责

| 环境 | 允许做什么 | 不做什么 |
| --- | --- | --- |
| Mac | 编写两个仓库的代码；运行单测；运行浏览器和助手；构建安装包 | 不把测试代码直接复制到服务器 |
| 腾讯云 staging | 运行测试版 BPMS、数据库和 OSS；执行迁移；接受 Mac 联调 | 不直接编辑代码；不使用生产数据库 |
| 生产服务器 | 运行已验收的固定 commit/tag | 不直接 pull 未验收的 `main`；不现场改代码 |

## 标准流程

1. 在 Mac 上为一个功能创建两个分支，例如 `feat/dewu-batch-listing` 和 `feat/dewu-batch-listing-helper`。
2. 先完成 BPMS 的 API、迁移和网页代码，提交并推送。
3. 腾讯 staging 只检出明确的 BPMS commit，应用迁移并重启服务。
4. Mac 浏览器和助手都连接 staging，验证任务领取、文件下载、状态回传、重试/终止和实际得物流程。
5. 两个仓库都通过测试和手工验收后，分别合并 PR 并创建 tag。
6. 生产只部署这两个 tag 对应的 commit，并记录版本对应关系。

## 版本记录

每次跨仓库发布或 staging 联调记录以下信息：

```text
BPMS_COMMIT=<commit-or-tag>
HELPER_COMMIT=<commit-or-tag>
MIGRATIONS=<applied-migration-ids>
STAGING_CHECKED_AT=<timestamp>
PR_BPMS=<url>
PR_HELPER=<url-or-multiple-urls>
STAGING_RESULT=PASS|FAIL|BLOCKED
MANUAL_CASES=<checked-and-unchecked-cases>
WINDOWS_E2E=PASS|FAIL|BLOCKED_NO_WINDOWS
CERT_EXPIRY_CHECKED_AT=<timestamp-or-N/A>
```

`STAGING_RESULT=PASS` 只表示 Mac 浏览器/助手完成了清单中的 staging 场景，不等于 Windows 安装包或生产发布已验收。

## 腾讯云域名和 IP

当前 `bookthink.cloud` 的 `@` 和 `www` A 记录都指向 `101.34.90.101`；`staging.bookthink.cloud` 已解析到同一 IP。

```text
staging.bookthink.cloud      A      101.34.90.101
```

staging 网关已启用 80/443 入口和 HTTPS，联调固定使用 `https://staging.bookthink.cloud`，不再把“新增域名/配置 HTTPS”当作待办。生产继续使用 `www.bookthink.cloud` 或现有生产域名。

证书自动续期不在本次工作范围内。每次联调或发布记录 `CERT_EXPIRY_CHECKED_AT` 和证书到期时间；到期前的续期提醒、续期验证和异常处理由后续运维流程负责。未完成证书检查时，不得把记录标记为完整发布验收。

### IP 加端口的限制

- 浏览器临时访问网站：`http://101.34.90.101:端口` 可以使用，但只适合临时网页检查。
- 助手访问远程 API：普通 `http://IP:端口` 不允许。助手会拒绝非 HTTPS 远程地址，任务文件下载也有可信来源校验。
- `https://IP:端口` 只有在证书的 SAN 明确包含这个 IP 时才可靠；自签名证书还会被客户端拒绝。
- 使用 `https://staging.bookthink.cloud`。助手需要显式设置 `EBAYDA_ALLOW_STAGING_API=1` 才接受 staging HTTPS 地址。
- 若 staging HTTPS 临时不可用，可以用 SSH 本地端口转发做故障隔离测试：助手连接 `http://127.0.0.1:本地端口`，并设置 `EBAYDA_ALLOW_LOCAL_API=1`。这不是团队共享的 staging 地址，也不能替代 staging 联调验收。

staging BPMS 示例配置：

```text
AUTOMATION_PUBLIC_BASE_URL=https://staging.bookthink.cloud
```

Mac 助手 staging 示例配置：

```text
EBAYDA_API_ORIGIN=https://staging.bookthink.cloud
EBAYDA_ALLOW_STAGING_API=1
```

生产助手不设置 staging 开关，保持默认生产地址。

## Windows 环境阻塞

Mac 可以运行 Python 单测、协议解析和可注入的运行时检查，但当前没有 Windows 主机，不能完成 Windows 专属验收：安装/卸载、`ebayda://` 协议注册、系统 Chrome 启动、DPAPI/用户目录行为、SmartScreen 和安装包升级。记录中必须写 `WINDOWS_E2E=BLOCKED_NO_WINDOWS`，不能仅凭 Mac 测试把 PR 标记为 Windows 已验收或进入生产发布。Windows 主机可用后，再补齐这些场景并把证据链接回两个 PR。

## 腾讯 staging 部署

不要在服务器上修改代码。服务器目录必须是干净的 Git worktree。使用仓库中的 `ops/deploy-staging.sh`，只检出指定 ref：

```bash
STAGING_SSH=myself_tencentcloud_root \
STAGING_APP_DIR=/opt/ebayda/bpms \
STAGING_REF=<bpms-commit-or-tag> \
STAGING_SERVICE=bpms \
STAGING_APPLY=1 \
ops/deploy-staging.sh
```

脚本发现服务器 worktree 有未提交改动时会停止，不会覆盖现场文件。数据库迁移必须在 staging 单独执行并记录迁移编号。

## 合并门禁

- `main` 只接受 PR，不直接开发。
- PR 必须写测试命令、测试结果、数据库迁移、跨仓库依赖和未完成的手工验证。
- 不使用 `git add .` 把临时对比文件、缓存或安装包带入提交。
- 任何生产发布都必须能用上一个 tag/commit 回滚应用代码；数据库变更必须先确认兼容性。
